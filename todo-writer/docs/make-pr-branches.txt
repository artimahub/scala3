===============================================================================
 Building one PR branch per week from fable-scaladoc-weeks-3-11
===============================================================================

 Run these yourself, block by block. Nothing here is automated: each week is a
 self-contained block you can run, inspect, and push before moving on.

 Weeks 3, 4 and 5 ADD ONE COMMIT to the branch that is already on origin, so
 those PRs update in place and no -2 branches are created. Weeks 6 through 11b
 have no existing branch, so each starts fresh off current main.

 Everything below was dry-run in a throwaway worktree (since deleted; no
 branches were left behind): weeks 3-5 onto their existing origin branches,
 weeks 6-11 onto main = 804dd160a1. Every one applies CLEANLY except week 11b,
 which hits one expected conflict on a todo-writer file; the fix is spelled
 out in that block. The verify helper below was run as written.

 Nothing was merged into fable-scaladoc-weeks-3-11. Each branch is built
 directly on current main, so any upstream drift is resolved by the
 cherry-pick itself, per week, where you can see it.


-------------------------------------------------------------------------------
 WHY SOME WEEKS NEED MORE THAN ONE CHERRY-PICK
-------------------------------------------------------------------------------

 Weeks 3-6 exist as TWO commits on fable-scaladoc-weeks-3-11: the original
 pipeline commit, and the later revision commit that rewrote it. The revision
 is a diff against the pipeline commit, so it only makes sense on top of that
 pipeline content.

 For weeks 3, 4 and 5 that pipeline content is ALREADY on origin, as the
 branch behind the open PR. So those weeks pick up only the REVISION commit
 (plus, for week 3, its audit fixup) and add it as one new commit to the
 existing branch. I checked this file by file: each existing branch matches
 its pipeline commit exactly, apart from upstream code drift in two files
 (Option.scala gained @publicInBinary, Regex.scala gained a captureChecking
 import and two self-type annotations). The cherry-picks leave that drift
 alone and touch only comments; I confirmed the resulting documentation is
 byte-identical to fable-scaladoc-weeks-3-11 in all 163 files across the three
 weeks.

 Week 6 is different: there is no scaladoc-missing-docs branch for it on
 origin (its PR was never opened, since week 6 was still partial then). So
 week 6 takes BOTH its commits onto a fresh branch off main, like weeks 7-11.

 Weeks 3 and 9 also get fixup commits from the 2026-08-24 audit: doc comments
 that had been left below an annotation (where the parser drops them), and one
 that had been written inside a commented-out block in mutable/Map.scala.

 Week 11b is four commits: the part-2 batch, the two hand-finished maps
 (LongMap, TreeSeqMap), and the final part-2b batch.

 The recipe is the same everywhere:

     git cherry-pick -n <commits...>     # apply, staged, but do not commit
     git commit -m "..."                 # one commit for the whole week

 -n (--no-commit) is what gives you ONE new commit instead of several.

 VERIFY HELPER (paste once per shell; used at the end of every week block)
-------------------------------------------------------------------------------

# Checks the branch you are standing on against a reference commit:
#   1. every changed file differs from that reference in comment lines only
#   2. no TODO FILL IN markers survive
#   3. no doc comment sits directly below an annotation (the parser drops those)
#
# Weeks 6-11 build on current main, so plain "verify" is right for them.
# Weeks 3-5 build on an OLDER base (their existing branch predates today's
# main), so comparing against main would drown you in unrelated upstream
# changes. For those, pass a reference explicitly:
#     verify HEAD~1                        # is the commit I just added comment-only?
#     verify $(git merge-base main HEAD)   # is the whole PR comment-only?
verify() {                       # usage: verify [ref]   (ref defaults to main)
  ref=${1:-main}; bad=0; n=0
  for f in $(git diff --name-only $ref -- 'library/src' 'library-js/src'); do
    n=$((n+1))
    if [ -n "$(diff <(git show $ref:$f | grep -vE '^[[:space:]]*(\*|/\*\*|\*/)' | grep -v '^[[:space:]]*$') \
                    <(grep -vE '^[[:space:]]*(\*|/\*\*|\*/)' "$f" | grep -v '^[[:space:]]*$'))" ]; then
      echo "  NOT COMMENT-ONLY: $f"; bad=$((bad+1))
    fi
    if [ "$(grep -ac 'TODO FILL IN' "$f")" != "0" ]; then
      echo "  LEFTOVER MARKER:  $f"; bad=$((bad+1))
    fi
    hits=$(awk '
      /^[[:space:]]*\/\*[^*]/ { inblk=1 }          # entering a plain /* ... */ region
      inblk { if (/\*\// ) inblk=0; next }
      /^[[:space:]]*$/ { next }
      ann && /^[[:space:]]*\/\*\*/ { print FILENAME ":" NR }
      { ann = ($0 ~ /^[[:space:]]*@[A-Za-z_`]/ &&
               $0 !~ /(^|[^A-Za-z])(def|val|var|class|trait|object|type|given|enum)([^A-Za-z]|$)/) }
    ' "$f")
    if [ -n "$hits" ]; then
      echo "  DOC BELOW ANNOTATION: $hits"; bad=$((bad+1))
    fi
  done
  echo "  files: $n   problems: $bad   (compared against $ref)"
}

-------------------------------------------------------------------------------
 IF SOMETHING GOES WRONG IN A BLOCK
-------------------------------------------------------------------------------

# A cherry-pick stopped and you want out, before you have committed:
git cherry-pick --quit
git reset --hard HEAD
git clean -fd

# Undo the commit you just added to an existing branch (weeks 3-5), as long as
# you have NOT pushed yet:
git reset --hard @{u}         # back to what origin has

# If you already pushed and want it gone, that one does need a force push:
git reset --hard @{u}~1
git push --force-with-lease origin <the-branch>

# Throw away a new branch (weeks 6-11) and start that week over:
git switch main
git branch -D <the-branch>

# See what a single commit did, before or after picking it:
git show --stat <sha>

# See exactly what your added commit changed on an existing branch:
git show --stat HEAD
git diff HEAD~1 -- library/ | head -100

 with a Scala-aware tokenizer, and compared against the pre-project baseline

   doc comments inserted inside a STRING literal .......... 0
     Every string literal in all 449 files is byte-identical to the baseline,
     so nothing was written into an @implicitNotFound message or any other
     string. (The scanner was self-tested on a synthetic case to confirm it
     would catch one.)

   doc comments left BELOW an annotation .................. 5, all now fixed
     library/src/scala/sys/SystemProperties.scala   wrapAccess       -> 4199d44413
     library/src/scala/collection/mutable/AnyRefMap.scala  4 sites    -> 28afc16801

     library/src/scala/collection/mutable/Map.scala  remove          -> 23dc7b1f04
     (A second such case, in immutable/List.scala, had already been removed
     before 69deef6cf6 was committed.)

   leftover TODO FILL IN markers .......................... 0
   non-comment (code) changes ............................. 0 across 449 files
   malformed @throws tags ................................. 0
   em-dashes introduced ................................... 0
     (25 exist in these files, all of them pre-existing on main.)

 So the answer to "did Fable and Opus fix those as they went": the string
